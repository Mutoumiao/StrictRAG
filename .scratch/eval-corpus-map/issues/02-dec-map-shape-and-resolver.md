## Question

工单 01 的事实到手后，裁定下面四组问题，每组给出**一句话结论 + 理由 + 被否掉的方案**。裁定必须落在「收紧或逐位等价」这一侧，**不许**放宽任何门。

1. **账本的形状与落点**：逻辑 id → `documents.id` 的映射账本长什么样（键、是否含 `kbId` / `tenantId` / 生成时刻 / 语料指纹 / 每条 id 的来源文件），放在哪（`artifacts/` 下的 gitignore 产物 · 仓内提交的 fixture 侧文件 · 由入库入口打印后由人粘贴）。**约束**：`fixtures/` 的**数据文件**不可改；uuid 因环境而异，故不该提交进版本库 —— 但「可核对」要求它可被第三方重建。给出**可核对**的判据（第三方拿同一份夹具 + 同一条命令，能否重建出等价账本）。
2. **解析落点**：映射在哪一层被应用 —— ① 跑批 CLI 读账本后**在比对前**把 `expectedDocIds` 逐条替换为 uuid；② 在 gold 加载器里解析；③ 在入库入口把 uuid **写回夹具**（**已被明令禁止**，只在裁定书里写明它为何被否）。选定方案要写清**默认行为**（不传账本参数时与今天逐位一致）。
3. **未映射 / 账本不可用时的行为**：三种情形分别怎么处理 —— (a) 没传账本；(b) 传了账本但某逻辑 id 不在里面；(c) 账本与当前 KB 对不上（`kbId` 不匹配 / 文档已不存在）。**硬约束**：`hitAtK` 必须是**真比值且缺映射算 miss**，**绝不允许**把缺失变成 `null`（PRD「有标注时」的语义不可被挪用）；同时要**响亮**（报告里能一眼看出「这是没映射，不是检索差」）。给出报告侧的落点（哪个键 / 哪个 reason），并说明它**为什么不是放宽**。
4. **新鲜度与失效**：账本什么时候算过期、过期时跑批该**拒跑**还是**继续但标注**。至少覆盖：KB 换了、夹具文件被改（指纹变）、账本里的 docId 在库内查不到。给出一个**机械可判**的口径（不靠人眼）。
