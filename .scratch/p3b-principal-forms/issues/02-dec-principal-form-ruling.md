# 裁定：ADR-057 §5 的「或等价结构化字段」是否已被满足

Type: grilling
Status: resolved
Blocked by: 01

## 问题

按 `01-research-principal-forms.md` 的事实面，裁定下列三件事，并给出**可核对的表述**（能被下一次核查直接引用）：

1. **等价性**：本仓今天「部门轴走 `ownerDeptId` + `visibilityLevel` 结构化展开、用户轴走裸 uuid 名单」的组合，是否已经满足 ADR-057 §5 的主体集合要求？
2. **`user:` 前缀语法**：`aclPrincipals` 的元素要不要带 `user:` 前缀？改与不改各自的代价与回归面。
3. **`role:…` 主体**：ES PRD 提到 `role:…`，而 ADR-057 §5 的必达清单未点名。裁定它属必达 / 可选 / 雾。

## 完成判据

- 每个子问题都有**裁定 + 依据（文本行号 / 源码路径）**，并写清「若换个读法会怎样」。
- 明确写：本次裁定是否**触碰 `prds/00–11`**；若触碰，则本图不能落，须 ADR → 改 PRD → 升版（写明并划出）。
- 明确写：落地后数据面的可见集合是**逐位等价**还是**收紧**；若出现任何「放宽」（例如写入口从 400 改成 200），逐条列出并给可接受 / 不可接受的判据。
- 给出**回写清单**。

## Answer

### 裁定 0（总）

**部门轴已满足**；**用户轴语义已满足、记号未对齐**；**`role:` 不是必达**；**本仓选择不实现前缀记号与 role 主体**（两者的实现方向分别是「须迁移 + 写入口放宽」与「放宽」），把这三处偏离**据实记为债并写明销账路径**，**不宣告「已对齐冻结文本」**。本次裁定**不改 `prds/00–11`**，因此**不触碰冻结语义**；但**也正因为不改冻结文本，它无法「销账」——销账路径留给 ADR 或实现**（见裁定 4）。

### 裁定 1 · 部门轴：**已满足** §5 的「等价结构化字段」支

**依据**（研究 §3.2 已逐条核实）：

- ADR-057 §5 末句（`prds/11-decisions/00-adr-index.md:1865`）逐字许可另一种形态：「文档/chunk 反范式 `aclPrincipals`（**或等价结构化字段**：`owner_dept_id` + `visibility_level` 由检索层展开为可匹配条件）」。
- 本仓走的正是该支：`dept-acl.ts` 的 `effectiveLevel` / `grantEffectiveLevel` / `isDocVisibleForDeptAcl` / `collectVisibleOwnerDeptIds` / `maxVisibleLevelUpperBound`，加上 `es-sparse.ts` 的部门组与级别组。**§3/§4 的四条规则逐条兑现**：级别门槛（`eff >= vis`）、上级看下级（`isAncestorPath` + `inheritDown`）、grant 沿子树、库级文档（`ownerDeptId == null` 独立规则）。
- **反过来，§5 字面的枚举支 `dept:{id}:lv:{n}` 无法表达这四条**（研究 §3.2 的四行表：`≥` 比较、祖先、grant 子树、无部门记号），除非把「租户内全部部门 × 全部级别」写进文档 —— 那才是「改冻结语义的形态」。故**不采纳枚举支**，且这不构成偏离。

### 裁定 2 · 用户轴：**语义已满足、记号未对齐**

**依据**（研究 §3.1）：两侧都是**精确身份相等**（`doc-acl.ts` 的 `principals.includes(userId)`；`es-sparse.ts` 的 `term aclPrincipals: uid`），**可读集合逐位一致**；差别只有三处：① 记号（裸 uuid vs `user:{id}`）② 集合 vs 单值入参（ES PRD §4.5 声明 `userPrincipals?: string[]`，仓内是 `aclPrincipalUserId?: string`）③ 无身份展开器（ES PRD §4.2 要求「由身份服务展开」；用户轴上展开是平凡的）。`null` / `[]` / 非空的语义边界与 ADR-009 决策 4、ES PRD §4.3、术语表、安全 PRD §3.6.1 四处**逐条一致**（研究 §3.3）。

**裁定：不实现前缀记号。** 三条理由：

1. **须迁移**：PG 列是 `uuid[]`（`packages/db/src/schema/kb/documents.ts` + migration `0014`），写 `user:…` 会在 PG 层直接失败；改列类型需要一条新 migration 且要处理存量行。（研究 §4.1 已核实；「失败的具体错误类别」为只读推断、未实跑。）
2. **写入口必然放宽**：4 个写入口（complete / write / PATCH / PUT acl）今天逐元素硬校验 uuid。带形状校验的放宽虽可接受（仍拒 `'x'`、`' '`、`'user:'`），但它**换不来任何可读集合上的收益**（裁定 2 前段），却要在契约、回读 schema、列表 schema、`aclTightens` 四处同步，并**必须**同时保留裸 uuid 兼容——否则存量文档整体掉出可读集合（静默加严）。风险与收益不成比例。
3. **对照本仓红线**：`Claude.md` 的「门禁只加严不放宽」；此处放宽的是**写入口的元素形状校验**，为 0 收益付红线风险不划算。

**若换个读法会怎样**（研究 §3.6 的两读法）：取「字面读法」则 `:1862` 的 `user:{id}` 今天未达标，本图**不能**只靠镜像闭合，须(a) 出一条读法 ADR（说明「裸 uuid ≡ `user:{id}`，前缀为 wire 记号」）或(b) 按上面的实现路径落地。**本裁定取「实质读法用于判定可见集合、但不用于宣告对齐」**：即**承认字面未对齐并记为债**，避免把「没做」写成「已做」。

### 裁定 3 · `role:…`：**不是 ADR-057 的必达项**，且本仓保守不做

**依据**（研究 §1.1 逐条核实）：ADR-057 §5 `:1862-1864` 的「至少含」列表**只有** `user:{id}` 与 `dept:{deptId}:lv:{effectiveLevel}`；`role:…` 只出现在 ES PRD 字段表（`:75`，带「等」）、ES PRD 查询示例（`:114`）、安全 PRD（`:210`，带「等」）—— **举例项，非必达**。

**并且实现它属放宽方向**：多一类主体只会让**更多人**读到文档，不会让任何人读不到。故本仓「未上 role 主体」是**保守**选择，不构成欠债意义上的风险敞口。

**连带纠错（必须回写）**：`docs/testing/coverage/02-acl.md` 原写「`aclPrincipals` 的角色 principal 主体形态未落（**ADR-057 要求**，…）」——**归属错误**，须改为「ES PRD 字段表/查询示例的举例项」。

### 裁定 4 · 销账路径（本图不落）

三处偏离的共同销账 = **ADR → 改 PRD → 升 `prds/README.md` 版本**（本仓既定序）；或对第 1 项走「实现前缀」路径（迁移 + 契约形状 + 读侧双形态兼容）。两条都**不在本图**：前者要改 `prds/00–11`（本图 Out of scope），后者要动数据形态与写入口门禁。
